## Delivered S1 Contract

- Eight verticals, three profiles, and all 17 route ids are config-driven.
- Business vertical and visual theme are independent axes. `config.vertical`
  owns fixtures/content, weather capability, Care label, default profile, and
  orders. `config.theme` owns only the validated HTML `data-theme` CSS skin.
- `portalProfiles` is the single production authority for nav, primary action,
  enabled modules, calendar mode, cart behavior, and drawer title. Vertical
  defaults select a profile and supply the Care label/theme facts.
- Health and Beauty use `appointments`, MonthCalendar, cart, and no weather.
  Activity is disabled for appointments while profile remains enabled for the
  avatar route.
- Health/Beauty fixture data contains accepted presentation facts only. Missing
  weather returns `null` and never falls back to Snow data.
- Care exposes deterministic module/session/control-plane placeholders. Denied
  states retain the shared `unauthorized` visual while `data-access` and
  `data-reason-code` distinguish `not-entitled` from `forbidden`. There is no
  Care adapter, normalizer, protected payload, or protected payload state.
- `seo.landing` is a public parity placeholder, not the standalone public CMS
  document owned by S3/S6.
- Detail routes use `/orders/:id` and `/proposals/:id`; encoded ids round-trip,
  malformed percent encoding follows unknown-route handling without throwing,
  and query strings are scoped to the orders or proposals route family.
- The obsolete fixture `profiles`/`profileFor` registry and exports are removed.
- Existing six verticals, onDemand/stormOps, auth/default/disabled guards,
  mode persistence, weather commands, and pricing/products PIM remain covered.

## Validator Cycle 1

The validator returned three actionable groups:

1. `runtime/manifest.json` omitted Care from onDemand/stormOps navigation and
   did not accurately express profile enabled-module semantics.
2. `config-behavior-check.mjs` proved only profile selection and Care-label
   presence, not the complete three-profile contract for every vertical, and
   had no direct manifest-to-runtime contract comparison.
3. The manifest retained a stale `~47` JavaScript claim and an incomplete
   `data-state` grammar.

Remediation:

- Manifest profile entries now use machine-readable nav objects. All three
  include `{ key: "care", labelSource: "verticalProfiles.careNavLabel" }` in
  the accepted position.
- Enabled modules moved into `portalProfiles.modules`, making module selection
  part of the same profile authority as nav/calendar/cart. Explicit
  `hvac + stormOps` now receives the exact stormOps module set unless
  `portalEnabledModules` explicitly overrides it.
- Manifest profiles record exact vertical membership, nav, enabled modules,
  primary label/action, weatherCalendar, calendar variant, showCart, and drawer
  title. The test imports `config.js` and deep-compares all these fields.
- Every one of the eight default vertical browser cases asserts exact visible
  nav order/labels, enabled modules, primary label/action, calendar DOM variant,
  cart visibility, theme, default profile, and absence of CMS-authored Care
  entitlement defaults. Explicit HVAC + stormOps override coverage remains.
- The test counts runtime files recursively and compares the manifest to the
  actual inventory: 53 JavaScript files under `runtime/src`, 54 total runtime
  JavaScript files including `data/fixtures.js`, and 6 stylesheets.
- The manifest no longer contains `~47`. Its shared `data-state` grammar now
  includes existing production `ready`, `loading`, `empty`, `error`, `fallback`,
  `disabled`, `unauthorized`, `validation-error`, `pending-action`,
  `success-toast`, `drawer-open`, `mobile-navigation-open`, and `active` states.
  Existing component/entity-specific states remain delegated to their actual
  component contracts and `scenarios.json`; no new state was invented.

## Validator Cycle 2

Finding:

- `applyPortalConfig` used `config.theme` to select `state.theme`, fixture
  orders, and weather compatibility, while `app.render` inferred HTML
  `data-theme` back from that content state. A visual override therefore changed
  business behavior and could let a weather-capable skin bypass Health/Beauty
  profile compatibility.

Remediation:

- `readPortalConfig` no longer derives a missing business vertical from
  `portalTheme`; an isolated visual theme override leaves the business default
  at HVAC.
- `resolveProfile` checks weather compatibility only against the business
  vertical. Health/Beauty reject stormOps even when `config.theme="snow"`;
  explicit HVAC + stormOps remains valid.
- `applyPortalConfig` now sets content `state.theme` and fixture orders from the
  business `verticalConfig`. It stores the independently validated visual theme
  only in `state.config.theme`.
- `app.render` writes HTML `data-theme` directly from `state.config.theme`.
- `theme.pick` remains an existing fixture vertical switch and intentionally
  sets both axes together. No end-user visual-theme picker was introduced.
- Manifest wording explicitly separates `config.vertical` business/content
  ownership from `config.theme` CSS-token ownership.
- The exact config harness now proves HVAC business content/orders under a Snow
  visual skin. It also proves Health and Beauty content, appointments profile,
  zero weather orders/feed/banner/card, and MonthCalendar under the same Snow
  visual skin, plus stormOps rejection for both verticals.
