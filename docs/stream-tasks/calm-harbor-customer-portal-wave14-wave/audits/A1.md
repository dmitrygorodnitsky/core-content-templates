# A1 Audit — Calm Harbor Customer Portal Wave 14

## Verdict

Accepted for the bounded `current-staging` demonstration. The CMS package now renders the Wave 14.1 Calm Harbor shell, read-only Orders, Services & prices, browse-only Shop, account menu, account bootstrap states, and the honest support-unavailable dialog over the existing live read rails.

This is not a production authorization approval. Generic Core list endpoints still need backend-enforced customer row isolation before this pattern can be promoted beyond the bounded staging case.

## Source and visual evidence

- Designer source remained immutable under `app-templates/customer-portal/design-inbox/**`.
- `shell.css`, `components.css`, `routes.css`, and `responsive.css` were transferred byte-for-byte into the runtime style layer.
- `evidence/visual-report.json` records 12 paired reference/implementation rows: Orders, Services, and Shop at 390, 768, 1180, and 1440.
- All measured horizontal positions and widths match exactly (0 px recorded drift; accepted tolerance 2 px).
- Stable component heights also match except the Orders aggregate at 768, where the reference's authored long fixture reference wraps to an extra 17 px. The live implementation deliberately renders only the shorter backend Order id because no separate backend reference field is proven. The row primitive itself remains the same height and width.
- Twenty-four paired PNGs are stored under `evidence/screenshots/`.

## Data and behavior evidence

- OIDC remains authorization-code + PKCE through the discovered same-origin Core contract.
- The authenticated User resolves to exactly one `SPA_CUSTOMER` Account; zero or multiple rows fail closed.
- Orders are queried with the resolved `account.id`; CMS and URL state cannot select the Account.
- A returned Order whose Account does not match the resolved Account fails closed.
- Raw Order status codes remain unmapped and read-only. No appointment date, specialist, location, tracking, invoice, detail route, or mutation is inferred.
- Services, membership offers, and Shop rows use only public PIM fields.
- Booking, cart, checkout, profile writes, order writes, appointment UI, and support delivery claims remain absent.
- Every support affordance terminates in `support-unavailable`; nothing claims a message, ticket, or conversation was created.

## Residuals

1. Backend row-level customer isolation is not yet proven on the generic list endpoints. Browser filters are defense-in-depth for this staging demo, not a security boundary.
2. Appointments and all write commands remain blocked until dedicated customer-scoped read/write contracts and backend-owned status mappings exist.
3. The CMS runtime depends on same-origin deployment and the configured Core/OIDC/PIM endpoints.
4. No live CMS upload or publish was part of this wave.
