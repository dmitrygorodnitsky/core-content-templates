# S3 — Customer-Scoped Read Adapters (W2)

Date: 2026-07-26. Depends on the applied seed in `evidence/S1.md`.

Status: **done.** Appointments, plans, purchases, and profile all read from live
Core against the applied seed, each verified with a real customer session.

## 1. Standing Rule for Every Adapter in This Slice

Core has no customer scoping (`evidence/S1.md` §6) and that gap is an accepted
residual for this single-client demo. Every read below therefore narrows to the
signed-in customer **in the adapter**, and every envelope reports
`scopeMode: "customer-filtered-client-side"`. The name is deliberate: the
narrowing is presentation. Core still returns the whole tenant to any portal
session, and nothing in this slice may be described as an authorization
boundary.

A second constraint shapes the implementation: **Core cannot filter on dynamic
attributes and fails silently** — a filter on `attributes.CUSTOMER_ACCOUNT`
returns `200` with zero rows rather than an error. Any entity whose customer
link lives in an attribute must be narrowed client-side.

## 2. Appointments — done

`runtime/src/adapters/core-spa-demo-adapter.js`.

- `loadCoreAppointments` still asks Core for `type.code = SPA_VISIT`, then keeps
  only rows whose `CUSTOMER_ACCOUNT` attribute equals the resolved account.
- `scopeMode` changed from `"tenant-demo-unscoped"` to
  `"customer-filtered-client-side"`. The envelope now reports both
  `resultSize` (the customer's rows) and `tenantResultSize` (what Core returned),
  so the gap stays visible instead of being hidden by the filter.
- With no resolved customer account the list is **empty**, never the tenant's.
- `createCoreAppointment` now writes `CUSTOMER_ACCOUNT`, `CUSTOMER_USER`, and
  `SERVICE_PRODUCT` on save. Without this a freshly booked visit would vanish
  from the customer's own list — the read and write paths must agree on the link.

Live result against staging with a real `SPA_CUSTOMER_PORTAL` session:
**3 customer rows out of 5 tenant rows**, `Grounding massage Aug 9 (Confirmed)`
as next, `Completed`/`Cancelled` correctly in the past list, and
`allowedActions` `reschedule` / `bookAgain` / none respectively. The two
excluded rows are the legacy demo appointments that carry no customer link.

`scripts/core-spa-demo-adapter-check.mjs` extended: another customer's
appointment must not reach the UI, an unlinked row is excluded, the tenant count
stays visible, a session without a resolved account gets an empty list, and a
booking save carries the customer attributes.

## 3. Plans — done

New `runtime/src/adapters/core-plans-adapter.js`, implementing the hybrid model
from `evidence/S1.md` §7.1 behind one list.

| source | becomes | key fields |
| --- | --- | --- |
| `SPA_PLAN_ENROLLMENT` project | `kind: "PACKAGE"` | `remainingUses` = `CREDITS_TOTAL - CREDITS_USED` (never stored twice), `totalUses`, `expiresAt`, `sourcePurchase` |
| `core-bill` `Subscription` | `kind: "MEMBERSHIP"` | `displayRecurringPrice` and `title` joined from the membership order line's price and product, `renewsAt` from `nextBillingAt`, `remainingUses: null` |

The normalized shape matches the accepted design fixture
(`runtime/data/fixtures.js` `spaCommerce.plans`) field for field, so the plan
card renders without any component change.

Workflow state maps to the approved customer vocabulary in **one table** in the
adapter (`ACTIVE → Active`, `EXHAUSTED → Used up`, `CANCELLED → Cancelled`), so
components never read raw states. A state outside that table raises
`plan-status-unmapped` rather than reaching the UI with a guessed label — see §5.

Live result: **3 plans** — `Harbor reset series` PACKAGE Active 4/5 with
`bookWithCredit`, `Skin ritual trio` PACKAGE Used up 0/3 with no actions, and
`Harbor membership` MEMBERSHIP Active `$18 / month` with `cancelRenewal`.
`renewsAt` is empty because the seed sets no `nextBillingAt`: an absent date is
omitted, never invented.

`scripts/core-plans-adapter-check.mjs` (new) covers the shape of both kinds, the
derived remaining balance, exclusion of another customer's enrollment, no reads
at all before the customer resolves, auto-renew off meaning no cancellation

## 4. Purchases — done

`runtime/src/adapters/core-orders-adapter.js` no longer returns a raw order
list. It now emits the purchase read model:

- **`kind` comes from the lines**, not the order type:
  `SPA_ITEM_SERVICE|RETAIL|PACKAGE|MEMBERSHIP` map to the customer kinds, and a
  purchase carrying more than one becomes `MIXED`. Order type stays a single
  `SPA_ORDER`, exactly as decided.
- **`customerStatus` maps through one table** (`OPEN → Confirmed`,
  `IN_PROGRESS → In progress`, `COMPLETED → Fulfilled`,
  `CANCELLED → Cancelled`). `statusCode` keeps the raw state alongside it for
  diagnosis. An unmapped state raises `order-status-unmapped` — see §5.
- **Fulfillment is joined as its own dimension.** `Shipment` has no native order
  link, so the adapter matches `SOURCE_ORDER` client-side and returns
  `{kind, status, windowStartLabel, windowEndLabel}`. When a pickup is `READY`
  and the order is not cancelled, that is also what the customer must act on, so
  it surfaces as `customerStatus: "Ready for pickup"` with the accepted notice
  copy. An absent window produces no date rather than the epoch.
- **`lines` and `itemSummary`** are built from the real rows; the line title
  comes from the product behind the price.

Two invariants the checks now pin down:

1. **Account scope is validated for every returned row before anything else.**
   Previously the mismatch check sat inside normalization, so a foreign order
   with no lines could slip past the new line filter. A foreign Order now fails
   the load whether or not it carries lines.
2. **An Order with no lines is not a purchase.** Pre-Purchases seed rows and
   demo checkout artifacts are excluded rather than rendered with an empty kind,
   which would also crash `KindChip` on `kind.toLowerCase()`. The envelope
   reports `ordersWithoutLines` and `accountResultSize` so the drop is visible,
   never silent.

Live result against staging — **5 purchases** from 7 account orders, the two
excluded being line-less legacy rows:

| ref | kind | status | total | summary |
| --- | --- | --- | --- | --- |
| `order-core-10` | MIXED | In progress | $158.00 | Custom facial · Mineral bath soak |
| `order-core-9` | MEMBERSHIP | Fulfilled | $18.00 | Harbor membership |
| `order-core-8` | PACKAGE | Fulfilled | $510.00 | Harbor reset series |
| `order-core-7` | RETAIL | **Ready for pickup** | $168.00 | 2 × Harbor body oil, `Ready — please pick up by Jul 29, 2026` |
| `order-core-6` | SERVICE | Fulfilled | $145.00 | Grounding massage |

`scripts/core-orders-adapter-check.mjs` extended with: line-derived kind, MIXED,
the pickup overlay and its notice, a shipment belonging to another order not
attaching, the line-less exclusion with its counters, and the unmapped-state
rejection.

Ref prefixes stay `order-core-*`; the plans adapter emits `sourcePurchase` with
the same prefix so plan → purchase resolves. The accepted fixture's `pur-*` refs
are fixture-only, and `[data-purchase-ref^="order-core-"]` in the browser check
is an existing production contract.

## 4b. Profile — done

`runtime/src/adapters/core-user-profile-adapter.js` keeps its proven email
save-and-readback path and gains the least-data read the Spa Profile expects.

- **Phone comes from the customer Account's contact entries.** `Contact` has no
  endpoint of its own — it is a nested collection on `Account` — so the adapter
  reads the account and takes the first `PHONE` entry. A missing contact means a
  missing phone, never a placeholder, and the account id is re-checked on
  readback so another customer's contact can never supply it.
- **Phone stays read-only.** Only `edit-email` is in `allowedActions`; opening a
  contact write needs a scoped contract that does not exist.
- **Preferences remain explicitly unavailable.** They have nowhere to persist:
  `UserOrganizationPreferences` carries only `{id, user, optimistic}` with no
  value fields, and both `GET /api/user/preferences.json` and
  `GET /api/user/org-preferences.json` return empty on staging. `unavailableFields`
  reports `preferences`, and `phone` too when no contact exists.

The seed gained the matching row: `beautySpaEntities.ts` now gives the demo
customer a `PRIMARY` contact with a `MOBILE` `PHONE` entry, saved inline with the
Account and reusing existing contact and entry ids so re-runs update rather than
stack duplicates.

Live result: `email opanagushin@gmail.com`, `phone +1 512 555 0143`,
`allowedActions [edit-email]`, `unavailableFields [preferences]`.

`scripts/core-user-profile-adapter-check.mjs` extended with: phone read from the
contact entry, a contact with no phone entry yielding null, and a foreign
account never supplying the phone.

## 5. Design Gaps to Order, Not Improvise

Two workflow states exist in the seed with no accepted customer treatment. Both
adapters reject them loudly rather than inventing a label, and neither is
reachable from the current seed, so nothing is blocked today.

| state | entity | why there is no label | owed before |
| --- | --- | --- | --- |
| `EXPIRED` | plan enrollment | the accepted vocabulary is `Active`, `Expiring soon`, `Used up`, `Cancelled`; `Expiring soon` is a warning on a live plan, not a terminal state | W5 opens plan expiry |
| `RETURN_REQUESTED`, `RETURNED` | order | the accepted purchase vocabulary is `Confirmed`, `In progress`, `Ready for pickup`, `Fulfilled`, `Cancelled`; a return in flight has no card treatment | W4 opens cancellation and returns |

Each needs a design request before its wave opens — the expired-plan card, and
the purchase card for a return in progress and a completed return.

## 5a. Correction: Money Was Being Derived Client-Side

Raised by the backend team and confirmed. Three related errors, all mine, now
fixed.

**`OrderItem.amount` is the UNIT price, not the line total.** Core multiplies it
by `itemCount` for the order total. The seed wrote a pre-multiplied amount, so
every multi-quantity order was doubled: the retail order carried `grandTotal`
168 against a single line of 42 × 2. Fixed in
`core-ui/scripts/dev/beautySpaEntities.ts` and re-applied; that order now reads
$84.00, and every order's total again equals the sum of its lines.

**The purchase adapter derived a unit price by dividing.** `normalizeLine`
computed `displayUnitPrice = amount / itemCount` and presented `amount` as the
line total — wrong in both directions once the semantics are right, and a
violation of the standing rule that the browser never computes commercial
figures. It now shows the server's `amount` verbatim as the unit price. Core
exposes no per-line total, so `displayTotal` is **omitted** rather than
multiplied; the order-level figure comes from the server's own `grandTotal`.

**The plan's recurring price came from the wrong record, in the wrong currency,
with a silently missing period.** It read the order line's amount — which
records a single charge, not an ongoing rate — formatted it with a hardcoded
`$`, and appended a cadence read from `subscription.unit`, a field that does not
exist (Core keeps it under `cadence.{period,unit}`, which the list projection
does not return), so the period vanished without trace. The rate now comes from
the catalog `ProductPrice` behind the membership line, using its own
`AMOUNT_MINOR`, `CURRENCY`, and `INTERVAL`. No price attributes means no rate
shown.

The lesson for the remaining waves: **money is read, never assembled.** Where the
server does not provide a figure, the honest output is nothing at all. The Cart
API does return `unitAmount`, `lineAmount`, and `subtotal`, so W4 checkout has
server-owned totals available and must use them rather than repeating this.

## 6. Debt Handed to W3: Write Paths Clone a Seeded Row

The read paths are generic — they normalize whatever Core returns and would work
against a tenant with real records. The **write** paths in
`runtime/src/adapters/core-spa-demo-adapter.js` are not: both find an existing
row and clone its references instead of resolving them by code.

| command | what it clones | its own error message |
| --- | --- | --- |
| `createCoreAppointment` | organization, task, type, workflow from any existing `SPA_VISIT` | `A seeded SPA_VISIT is required for the current-api booking demo` |
| `createCoreOrder` | currency, organization, type, workflow from the account's newest Order | `A seeded Core Order is required for the current-api checkout demo` |

Consequences to fix when W3 opens booking, rather than now:

1. **Neither command works in an empty tenant.** A first-ever booking or
   checkout has nothing to clone from.
2. **A cloned reference can be the wrong one.** The order template is simply the
   newest row for the account, so a future order type or currency change would
   be silently inherited from whatever happens to be latest.
3. **The appointment reuses another visit's Task.** `appointment.task_id` is NOT
   NULL (`evidence/S1.md` §5.2) and the adapter satisfies it by pointing at the
   template's task, so unrelated visits end up sharing one task. Booking should
   create its own task under the customer's care plan, exactly as the seed now
   does.

The fix is to resolve type, workflow, currency, and organization by code — the
same lookups the seed performs — and to create a task per appointment. W3 has to
touch both commands anyway, so the change belongs there and is recorded here so
it is not mistaken for working production behaviour.
