# S5 — Appointment Commands (W3)

Date: 2026-07-26. Depends on `evidence/S3.md` and `evidence/S4.md`.

Status: **book and reschedule are live and proven; cancel is implemented and
unit-proven but blocked live by a backend fault (§4).**

## 1. The S3 §6 Debt Is Paid

Both write paths resolve their references by code instead of copying whichever
row happened to be newest.

| was | now |
| --- | --- |
| `createCoreAppointment` cloned organization/task/type/workflow from any existing `SPA_VISIT` | resolves `appointment-type` and `task-type` by code (each carries its own workflow), the organization by code, and the customer's care plan by its `CUSTOMER_ACCOUNT` attribute |
| `createCoreOrder` cloned currency/organization/type/workflow from the account's newest Order | resolves `order-type` by code, organization by code, and the currency from `config.currency` via the `dictionary` entity |
| booking reused another visit's Task to satisfy the NOT NULL `task_id` | creates its own task per visit, idempotent by code, hanging off the customer's care plan |

A tenant missing any of these now fails with a named contract error
(`appointment-type-missing`, `order-type-missing`, `organization-missing`,
`currency-missing`, `care-plan-missing`) instead of silently borrowing a
reference. Booking and checkout therefore work in a tenant that has no prior
appointment or order — the empty-tenant hole from S3 §6 is closed.

Two Core constraints found while doing it, both now encoded:

1. **A Task must belong to a Project.** Core throws
   `NullPointerException: Task.getProject()` otherwise. Booked visits hang off
   the customer's care plan, and the seed now stamps that plan with
   `CUSTOMER_ACCOUNT`/`CUSTOMER_USER` so the runtime can find it without
   hardcoding a customer-specific code.
2. **`project` must appear in the save *mappings*, not just the entity.** A Task
   save whose mappings omit it fails with
   `NullPointerException: Collection.size()`. This is the same class of trap as
   the dynamic-attribute filter: a shape error surfaces as an opaque 500.

## 2. Live Proof — Book and Reschedule

Run against staging with a real `SPA_CUSTOMER_PORTAL` session:

```
before: 3 customer rows of 5 tenant rows
booked: appt-core-9 Grounding massage Aug 20 Confirmed
replay same ref: true
after:  4 customer rows of 6 tenant rows
booked visit is in the customer's own list: true
rescheduled: appt-core-9 Aug 21 11:00 AM Confirmed
```

That proves, end to end: the booking creates exactly one appointment and one
task, a replayed `requestRef` returns the same appointment without a second
write, the new visit carries the customer link the read path filters on so it
appears in the customer's own list, and reschedule moves it with an
authoritative readback.

## 3. Cancel

`cancelCoreAppointment` is implemented to the honest-success rule:

- ownership is re-checked against the resolved account — a route id is never
  proof on its own;
- the command refuses states that cannot be cancelled and returns unchanged if
  the visit is already cancelled, sending no event;
- **a 2xx on `send-event` is not success.** Only the readback reporting
  `Cancelled` counts; otherwise the command fails with
  `appointment-cancel-unconfirmed`.

`allowedActions` now yields `["reschedule", "cancel"]` for a scheduled visit and
`[]` for a cancelled one, so the UI offers the action only when the workflow
does. Unit coverage in `scripts/core-spa-demo-adapter-check.mjs`: successful
cancellation with the exact event URL, the unconfirmed-readback rejection, the
already-cancelled no-op, the not-cancellable state, and the foreign-appointment
refusal.

## 4. Blocked Live: Workflow Event Dispatch Returns 500 Tenant-Wide

`POST /{service}/api/{entity}/{id}/send-event.json?event=…` fails with an opaque
`500 Internal Server Error` (no message body) for **every entity kind** —
appointment, project, shipment — and `list-events` returns an empty array for
every row, including ones whose workflow plainly defines an available
transition.

Reproduction, narrowed step by step:

| probe | result |
| --- | --- |
| `SCHEDULED-CANCELLED` on the portal-booked appointment | 500 |
| same, with the admin deploy session instead of the customer session | 500 |
| `SCHEDULED-IN_PROGRESS` and `SCHEDULED-NO_SHOW` on the same appointment | 500 — it is the appointment, not the event |
| after filling the optional `SERVICE_PRODUCT`/`SPECIALIST_ACCOUNT` attributes | 500 — not missing attributes |
| a fresh appointment created with the **seed's exact shape**, admin session, reusing a seeded task | 500 |
| `PENDING-READY` on the pickup shipment | 500 |
| `ACTIVE-EXHAUSTED` on an already-exhausted enrollment (a no-op) | 500 |
| `list-events` on a seeded scheduled appointment, an active enrollment, and a completed order | `200 []` in all three cases |

The failure is **not caused by the portal adapter** — it reproduces with the
admin deploy session, with a seed-shaped row, and on entity kinds the portal
never writes. The workflow definitions are intact:
`SPA_APPOINTMENT_LIFECYCLE` reports all five states and all four events.

**It regressed during this session, and the workflow seed change is not the
likely cause.** The order of events rules it out: `workflows.ts apply` added the
new states and events *first*, and the entity seed then drove real transitions
through this same call afterwards — orders to `COMPLETED`, appointments to
`COMPLETED` and `CANCELLED`, an enrollment to `EXHAUSTED`. Dispatch was working
after the workflow definitions changed.

The empty `list-events` is also not a symptom of anything this session did: it
returns `[]` for entities on workflows this session never touched
(`CORE_PROJECT_WORKFLOW`, `IT_RESOURCES` in the SYSTEM organization), so an empty
list is the endpoint's normal shape rather than evidence of breakage.

What remains unexplained is why dispatch stopped between the successful seed run
and the first cancel attempt. Everything applied in between was type and entity
data, not workflow definitions. Candidates, none confirmed:

- a `dev-1` restart or deploy in that window;
- a stale cache or index in the workflow engine that a restart would clear;
- something in the type re-application (attributes were added to seven types)
  that the engine reads at dispatch time.

`send-event` was deliberately **not** tried on an untouched SYSTEM-org entity:
that would mutate data belonging to other work. Diagnosing further needs a
server-side stack trace; nothing more can be established from the client. Until
it is resolved:

- **book and reschedule are open** — neither uses a workflow event;
- **cancel stays unavailable at runtime.** It is implemented and unit-proven,
  and it fails closed rather than claiming a cancellation that did not happen,
  which is the correct behaviour to ship while the backend is broken;
- the same fault will block **W4 order cancel/return** and **W5 plan
  cancellation**, which are workflow events too.

Diagnostic rows left on staging by this investigation, deliberately not deleted:
`CP_DEMO_APPT_W3_LIVE_1` (+ its task), `CP_DEMO_EVENTPROBE_1`,
`CP_DEMO_PROBE_TASK_M1`, `CP_DEMO_PROBE_TASK_ADMIN`.

## 5. Not Done in S5

- **Wiring cancel into `actions.js`.** `spaApptCancel` is still the fixture-only
  local mutation with a success toast, which is exactly the "a local click is
  not business success" violation in live mode. It should route to
  `cancelCoreAppointment` the way booking routes to `createAppointment` — but
  wiring it while the backend 500s would only surface a failure state, so it is
  deferred to the same fix.
- **Book again** needs no new command: it is a booking with a fresh
  `requestRef`, already covered.
- **Slot conflict handling.** With no server holds (accepted in
  `evidence/S1.md` §7.3), a conflict can only be detected after the fact. No
  conflict case exists in the seed to exercise it.
