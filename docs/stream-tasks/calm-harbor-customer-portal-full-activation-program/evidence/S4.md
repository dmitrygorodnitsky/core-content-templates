## 1. What Needed Wiring

Three of the four read surfaces were already wired to live module data by
earlier waves and only needed S3's adapters to supply the right shapes:

| surface | how it reads live | S4 work |
| --- | --- | --- |
| Appointments | `spaAppointments()` returns `state.moduleData.appointments` in live mode | none — S3's scoping flows straight through |
| Purchases | `SpaPurchasesPage` reads `state.moduleData.orders` and gates the mapped list behind the target capability | none — S3's purchase model flows straight through |
| Profile | `profileModule` selects the Core adapter in live mode | none |
| Plan | **not wired at all** — no `plan` module existed and `spaPlans()` read fixtures unconditionally | all of §2 |

## 2. Plan Module

- `runtime/src/modules/index.js` gained a `plan` module: `asyncOnly`, selecting
  `createCorePlansAdapter()` in live mode and an inert empty envelope in fixture
  mode, mapping `customer-forbidden` to `unauthorized` and surfacing an expired
  session on the account rather than the plan list.
- `spaPlans()` in `runtime/src/state.js` now returns the live envelope's items in
  live mode. A module that has not loaded yields nothing — never fixture plans —
  and the fixture-only local "cancelled" map no longer masks what Core returned.
- The live harness `runtime/calm-harbor-spa-live-demo.html` already declared
  `plan` in `data-portal-enabled-modules` under the `spaTarget` profile, so no
  configuration change was needed; the module it referenced simply did not exist.

## 3. A Message That Had Become False

`SpaPlanPage` short-circuited on `spaCurrentApiDemoOpen()` and rendered
*"Personal plan details aren't in the current API"*. That was true when the
design was accepted. After S3 it is not: packages and memberships now come from
Core.

Both treatments are accepted design, so this is a question of which state
applies, not new UI. The block is now gated on `isModuleEnabled("plan")`: a
deployment that does not enable the module still gets the accepted unavailable
treatment, and one that does gets the real plan list with its own
loading / error / empty / unauthorized gates.

The page also took its state from the fixture scenario (`state.view`). It now
resolves `state.moduleStatus.plan` first, exactly as `SpaPurchasesPage` does, so
live loading, error, and unauthorized reach the gate. That is a transfer of an
existing accepted pattern, not a new one.

## 4. Verification and Its Limit

`scripts/plan-module-check.mjs` (new, browser-free) pins: the module is
registered and async-only, the live adapter refuses foreign module ids, fixture
mode stays inert, failure envelopes map to accepted states, an expired session
surfaces on the account, the selector reads the live envelope, an unloaded
module shows nothing rather than fixtures, local cancellation cannot rewrite a
server status, and the unavailable block is gated on the module.

All adapter checks pass alongside it: orders, plans, spa-demo, account,
user-profile, and the fixture check.

**What is not verified here.** Page rendering and the route-state matrix run
through `scripts/s7-route-state-check.mjs`, `config-behavior-check.mjs`, and the
per-wave visual suites, all of which require Playwright. Playwright is not
installed on this machine and the failure reproduces with every change stashed,
so it is an environment gap rather than a regression. Consequently the following
remain **unrun**, not passed:

- pixel acceptance at 390 / 768 / 1180 / 1440;
- the route × state matrix for the plan route's live states;
- `[data-purchase-ref^="order-core-"]` browser assertions in
  `calm-harbor-current-api-browser-check.mjs`.

They must be executed in an environment with Playwright before W6 claims visual
parity. Nothing in this slice should be read as visual sign-off.
