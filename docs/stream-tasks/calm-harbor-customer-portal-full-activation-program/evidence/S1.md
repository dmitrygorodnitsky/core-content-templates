## 1. Method

Live inventory via the generic Core list API with the mapping syntax the portal
adapters already use (`core-spa-demo-adapter.js:12-41`):

- scalar `{ name }`;
- relation `{ key: "id", mappings: REF, name, type: "identifier" }`;
- collection `{ mappings: REF, name, type: "collection" }`.

A relation requested as a bare `{ name }` returns the entire nested entity
graph and, for large types, a ~1.2 MB response that is truncated into invalid
JSON and intermittently drops the connection. That is a client-side usage
error, not a backend defect: always use the `type: "identifier"` form.

## 3. Blocking Finding: Appointments Have No Customer Link

Probing every plausible relation on `core-svc/appointment` returns a value for
only three: `task`, `type`, `organization`. `account`, `customer`, `user`,
`client`, `resource`, `assignee`, and `project` are all null. Following the
chain further does not help — `task.project` resolves, but neither Task nor
Project carries an account either.

The reason is visible in the seeds. The access-probe types
(`core-ui/scripts/dev/seeds/customerPortalAccessProbeTypes.json`) attach the
ownership link as **dynamic type attributes**, `CUSTOMER_ACCOUNT`
(`com.pixelnation.account.domain.Account`) and `CUSTOMER_USER`
(`com.pixelnation.common.domain.User`), and
`customerPortalAccessProbe.ts:217-224` writes them per record. The Calm Harbor
types had no attributes at all, so `SPA_VISIT` records carry no customer
identity in any form.

Consequences:

- the appointments-first portal cannot scope appointments to a customer today,
  not even by a client-sent filter — the field does not exist;
- `core-spa-demo-adapter.js` filters only by `type.code = SPA_VISIT`, which is
  exactly why the current list is tenant-level;
- the same gap applies to the Care plan/task chain.

Orders are the exception: `core-bill/order` has a native populated `account`
relation, so Purchases can at least be filtered per account (still a client
filter, not a server boundary — the standing S0/contract finding).

### 5.2 Backend constraints discovered during the apply

Each of these forced a change to the seed and is worth carrying into W2+:

1. **`appointment.task_id` is NOT NULL.** Every visit must hang off a Task, so
   the seed now creates one `SPA_CARE_TASK` per appointment under the care-plan
   project. Booking in W3 must do the same.
2. **`Order`, `OrderItem`, `Shipment`, and `Inventory` have no `code` column.**
   Rather than overloading a standard field, those four types carry a dedicated
   `RECORD_CODE` string attribute (unique, seed-owned) that plays the role the
   missing `code` column would. `notes` stays free for its real meaning — the
   order's human label, the line's product code. The seed saves them through a
   predicate-based idempotent helper (`ensureByPredicate`) keyed on
   `RECORD_CODE`, with a legacy fallback so rows written before the attribute
   existed are updated in place instead of duplicated. Verified: after the
   migration run, orders 6–10, all six lines, the shipment, and both inventory
   rows carry their `RECORD_CODE` and kept their original ids; the four
   pre-existing demo/probe orders were left untouched.
3. **`subscription.payment_method_id` is NOT NULL**, and
   `subscription/create.json` throws `NullPointerException: paymentMethod`. See
   §9.
4. **`Shipment` never receives an initial workflow state**, and `send-event` on
   a stateless shipment returns 500. Fulfillment status is therefore carried by
   the `FULFILLMENT_STATUS` attribute (`PENDING|READY|COLLECTED|CANCELLED`); the
   workflow stays attached for the day the backend fixes initialisation.
5. **The staging edge intermittently drops write connections** (`ECONNRESET` on
   `product/save` and `product-price/save`). The seed's HTTP clients now retry
   transient socket failures up to four times with backoff; every call is
   idempotent, so replay is safe.

### 6.2 Findings

1. **Read authorization on the generic entity APIs is not enforced for this
   role.** The session carries 13 permissions and none of them cover User, Role,
   Account, Order, Project, Task, EntitlementGrant, AccountType, or ProductPrice
   — yet every one of those lists returns full tenant contents. This is not the
   role being wider than documented; the role is exactly as seeded.
2. **There is no row-level isolation.** Foreign account and foreign order are
   returned in full by both `list` (client-chosen filter) and `get` (direct id).
   A modified client simply changes the filter or the id.
3. **Failures are enumerating.** A foreign id returns 200 with data while a
   nonexistent id returns 404, so the two are trivially distinguishable — and
   the foreign case leaks the record itself rather than merely its existence.
4. **Delete is not gated either.** `delete.json` returned 200 for a
   customer-role session. The id was nonexistent, so nothing was destroyed and
   the call is a no-op, but no authorization denial fired before the operation.
   **This was deliberately not confirmed against a real record**, because doing
   so would destroy staging data; the 200 is strong evidence of a missing
   pre-authorization check, not proof that deleting a live row would commit.
5. **Two things do hold.** `cart/current` enforces a real server-side
   account binding — own `accountId` 200, foreign 403 — the only endpoint
   observed with row-level enforcement. And the org boundary holds: passing
   `X-Organization-Code: SYSTEM` did not widen scope beyond the session's own
   organization.

### 6.3 Accepted residual

Decided 2026-07-26: this posture is accepted for the program. The portal ships
as a single-client demo, so the absence of customer scoping is a known residual
rather than a blocker, and W2–W6 proceed. The backend items below stay on the

### 6.4 Consequence for the program

This confirms and sharpens the standing blocker in
`CORE-CUSTOMER-PORTAL-CONTRACT.md`, with direct evidence from a genuine
customer session rather than inference. The staging portal may keep using these
generic APIs for the demo, but:

- nothing in this posture may be described as tenant or customer isolation, in
  UI copy, package README, or evidence;
- promotion beyond a single-client staging demo stays blocked until scoped
  endpoints enforce read *and* write authorization server-side;
- W2 read adapters may filter client-side to the signed-in customer for the
  demo, but that filter is presentation, never a security boundary, and must
  not be documented as one.

Backend items to raise, in priority order: (a) delete/mutation authorization on
the generic entity APIs; (b) row-level scoping for Account/Order/Appointment
reads; (c) non-enumerating responses so foreign and missing are
indistinguishable; (d) `cart/current` returning 400 rather than a raw 500 when
`accountId` is absent; (e) the five constraints and defects in §5.2, of which
Shipment state initialisation and the Subscription payment-method requirement
are the two that changed the design. The `cart/current` account binding is the
model the other endpoints should follow.

## 7. Recorded Product Decisions

These are settled product decisions, restated here as implementation input.
They are not open questions and must not reopen before W2. The order/line model
is the one already written in
`content/cases/CALM-HARBOR-CUSTOMER-PORTAL-PRODUCT-CONTRACT.md:17`.

### 7.1 Plans — hybrid model

- **Membership** is a `core-bill` `Subscription` bound to the customer Account
  and its source Order.
- **Package** is a personal, customer-scoped plan instance carrying a finite
  visit balance.
- The portal exposes both through one unified `/plans` read model; the split is
  backend truth, not a UI concept.
- Existing org-level `entitlement-grant` rows are not used.

Technical form, chosen here because the probe showed the deployed
`entitlement-grant` cannot be bound to an Account (no account/user linkage is
returned, and the two staging rows carry no code or attributes): the package
instance is a typed `core-svc` Project, `SPA_PLAN_ENROLLMENT`, on the new
`SPA_PLAN_ENROLLMENT_LIFECYCLE`. Project was chosen over Order or Account
because it is the only typed entity in a service the portal already calls that
carries both a workflow and dynamic attributes, and enrollment is a
customer-scoped container rather than a commercial record.

| attribute | class | required | purpose |
| --- | --- | --- | --- |
| `CUSTOMER_ACCOUNT` | `account.domain.Account` | yes | customer scope |
| `CUSTOMER_USER` | `common.domain.User` | yes | session scope |
| `PLAN_PRODUCT` | `pim.domain.Product` | yes | the purchased `SPA_PACKAGE` |
| `SOURCE_ORDER` | `bill.domain.Order` | yes | the purchase that created it |
| `CREDITS_TOTAL` | `Integer` | yes | finite visit balance |
| `CREDITS_USED` | `Integer` | yes | consumed credits; `remaining` is derived, never stored twice |
| `VALID_UNTIL` | `LocalDate` | no | expiry when the package has one |

Memberships get **no** enrollment row and no guessed visit balance —
`subscription/create.json` takes `{orderId, paymentMethodId?, trialEnd?}`, so a
membership is created from its order with no payment method, consistent with
`SIMULATED`. Balance truth for packages is `CREDITS_TOTAL - CREDITS_USED` read
back from the server after every mutation; the browser never decrements
locally.

### 7.2 Orders — one type, kind carried by lines

One general `SPA_ORDER`; the purchase kind is the set of `OrderItem` types
(`SERVICE`, `RETAIL`, `PACKAGE`, `MEMBERSHIP`, and `MIXED` when a single order
carries more than one). Pickup is not an order type — it is a separate
fulfillment dimension (`kind=PICKUP`, status, window, location) carried by a
`SPA_FULFILLMENT` shipment. Order, fulfillment, Appointment, and plan
enrollment stay four independent dimensions. Seed shapes are in §4.

### 7.3 Booking without a server hold — accepted for staging/demo

S0 proved no slot/hold/intent contract is deployed. For the staging demo this
is accepted, not blocking, and W3 opens under these rules:

- the customer picks a slot; the UI never claims the slot is held;
- confirm performs save, and success renders only after authoritative readback
  of the created Appointment;
- conflict is detected after the fact and returns the customer to time
  selection;
- no local countdown and no "your time is held" copy.

A server-side hold remains required for production customer-scoped APIs; the

## 9. Membership Subscription — Resolved by an Offline Payment Method

The recorded decision (§7.1) is that a membership is a `core-bill`
`Subscription` bound to the customer Account and its source Order. The deployed
schema forces a payment-method record to exist first:

- `POST /api/subscription/create.json` throws
  `NullPointerException: paymentMethod`;
- `POST /api/subscription/save.json` hits
  `null value in column "payment_method_id" violates not-null constraint`;
- and on `AccountPaymentMethod` itself, **`provider` and `provider_pm_id` are
  also NOT NULL** — discovered one column at a time during the apply.

**Decision, 2026-07-26: seed one offline payment method.** The record is
`type: "OFFLINE"`, `provider: "OFFLINE"`,
`providerPaymentMethodId: "offline-CHS_STG_ELENA_RIOS"`, `enabled: true`, and
every card field left empty — `brand`, `last4`, `expMonth`, `expYear`,
`fingerprint`, `funding`, `country`, and `billing` are all null, verified by
readback. `provider` names the offline settlement path, not a processor: there
is no PSP, no token, and no external reference of any kind.

This satisfies the payment posture in full. No charge, invoice, receipt,
balance transaction, or refund is created, and the customer never sees a payment
method — the portal's checkout stays simulated. What the row means is "settled
at the spa", which is what the demo actually does.

The membership now exists: Subscription `ACTIVE`, bound to
`CHS_STG_ELENA_RIOS` and order `CHS_STG_ORDER_MEMBERSHIP`, `autoRenew` true,
monthly cadence, starting 2026-07-26.

The scope line this touches ("saved payment methods") is narrowed rather than
dropped: exactly one OFFLINE row with no card data is permitted as a foreign-key
requirement of Subscription; real payment instruments, PSP references, and any
card field remain out of scope. Rejected alternatives, for the record: modelling
membership as a `SPA_PLAN_ENROLLMENT` (diverges from the decided model and loses
`autoRenew`/`startsOn`/cadence) and making `payment_method_id` nullable (correct
long-term, unavailable on this deployment).

## 10. Runtime Follow-Up: RECORD_CODE in the Live Demo Adapter

`runtime/src/adapters/core-spa-demo-adapter.js` marked the orders it created by
writing its idempotency key into `notes`, the same overload the seed dropped in
§5.2. It now writes `RECORD_CODE` on the order's type and leaves `notes` as a
human label.

A backend trap made this more than a rename: **Core cannot filter on dynamic
attributes, and fails silently.** A list filtered on `attributes.RECORD_CODE`
returns `200` with zero rows rather than an error, while a bare `RECORD_CODE`
property returns 500. A naive port would therefore conclude "no existing order"
on every replay and create a duplicate each time. The adapter now issues one
account-scoped list — serving both the idempotency check and the order-template
lookup, one call instead of two — and matches `RECORD_CODE` client-side, with a
`notes` fallback so orders written before the attribute existed are still
recognised.

`scripts/core-spa-demo-adapter-check.mjs` was updated to the new contract and
extended with two cases it did not previously cover: replaying the same
`requestRef` must return the existing order without a second save, and a legacy
`notes`-marked order must still be recognised. The check passes.

This changes runtime source only. The deployed CMS package still carries the
previous bundle; rebuilding and re-uploading remains a separate, gated step.
