# S0 — API Inventory and Scoped-Contract Matrix

Date: 2026-07-26. Environment: `dev-1.servicewand.com` (staging).
Executor: automated inspection + live probes; read-only — no entity was
created, mutated, or deleted by S0.

## Method and Provenance

1. **Spec inspection.** OpenAPI documents pulled per service from
   `https://dev-1.servicewand.com/{service}/api-docs` with a bearer obtained by
   the `grant_type=api_key` exchange (deploy key from `core-ui/.env`):
   `core` (750 paths), `core-bill` (226), `core-pim` (172), `core-cms` (132),
   `core-svc` (127), `core-rm` (121), `core-acct` (46), `core-routing` (40).
2. **Live probes.** Read-only `list/get/basic-info` calls with
   `X-Organization-Code: CALM_HARBOR_SPA_STAGING`; exact results below. The
   probe identity is the SYSTEM deploy-key user, not a customer session —
   customer-role authorization semantics are S1 scope.
3. **Dynamic-type truth.** Core entities are dynamically typed; field contracts
   for Spa types come from the seed
   `core-ui/scripts/dev/seeds/beautySpaTypes.json`, not from OpenAPI schemas.

Known backend defect carried into this wave (user-reported, matches the
`--skip-reviews` guard in `core-ui/scripts/dev/beautySpa.ts`): **core-pim
ProductReview save is broken**. Review writes are excluded from seed and
command plans until fixed; review reads remain available.

## Cross-Cutting Conventions (proven live)

- Headers: `Authorization: Bearer …` + `Content-Type: application/json` +
  `X-Organization-Code`; the org header is omitted only for
  `POST /core/api/user/basic-info.json`.
- Generic entity API family, per entity, uniform across services:
  `list.json / get.json / save.json / size.json / commit.json / delete.json`
  plus `audit/*`, `fts/*`, and a sibling `*-state-transition` entity.
- List request: `{ filters: [{type, operator, property, value}], mappings:
  [{name}], offset, pageSize, sorting: [{field, direction}] }` →
  `{ resultSize, result[], sequence }`. Nested/relation properties are
  addressed with dotted `property` paths (e.g. `user.id`, `type.code`).
- Optimistic concurrency: rows carry `optimistic` (probed:
  `SPA_CUSTOMER` account row `{"optimistic":5,"id":1,"code":"CHS_STG_ELENA_RIOS"}`);
  save must send it back — this is the versioning primitive for W3–W5 commands.
- Idempotency primitive: unique `code` on typed entities; the proven
  `core-spa-demo-adapter` pattern is "list by code marker → save → re-read".

## Boundary Matrix

Statuses: **exists** (endpoint proven live), **exists-generic** (only the
generic entity API; scoping is the client's filter, not a server boundary),
**absent** (no endpoint family at all).

### 1. session/home — exists-generic

- `POST /core/api/user/basic-info.json` → 200. Returns authenticated user,
  roles, `organizationPath`, languages, config. No org header.
- Customer bootstrap = `POST /core-acct/api/account/list.json` with
  `filters [user.id =, type.code = SPA_CUSTOMER]` → 200; staging holds exactly
  one row: `CHS_STG_ELENA_RIOS` (id 1).
- **Gap:** no scoped `/me`/capabilities endpoint; module capabilities and
  attention summaries remain client-derived. No server rejection of
  browser-supplied account ids on the generic reads (see §authorization).

### 2. appointments — exists-generic

- `POST /core-svc/api/appointment/list.json` (`type.code = SPA_VISIT`) → 200,
  2 rows live. `get.json`, `save.json`, `size.json`,
  `appointment-state-transition/*` present.
- Statuses come from `SPA_APPOINTMENT_LIFECYCLE` workflow states; transition
  history via `appointment-state-transition/list.json`.
- **Gap:** list is tenant-level; the customer filter is a client-sent
  `filters` entry — not a server authorization boundary. Non-enumerating 404
  for foreign/missing ids is unproven → S1 probe with the customer role.
- `allowedActions` do not exist server-side; they must be derived from
  workflow state + program policy and validated per command in W3.

### 3. booking (slots / holds / confirm) — absent

- No slot, availability, hold, or booking-intent endpoint exists in any
  deployed service (searched all 1499 operations).
- The only write is `appointment/save.json`. Idempotent confirm is achievable
  via unique `code` + readback (proven adapter pattern). **Slot inventory,
  conflict detection, and expiring holds have no server contract.**
- W3 input decision: either accept save-based booking without server holds
  (conflict = post-hoc), or hold W3 per the W0 stop condition until a backend
  contract appears. Recorded as the primary W0 finding.

### 4. catalog (services / retail / sellability) — exists (public) + exists-generic (tenant)

Anonymous public catalog (no bearer), all probed 200:

- `POST /core-pim/public/{org}/catalog/price-comparison.json` — body
  `{productTypeCode, includeChildProductTypes, priceTypeCode:
  SPA_STANDARD_PRICE, priceAttributeCode: INTERVAL, priceAttributeValues
  [ONE_TIME, MONTH], currencyAttributeCode: CURRENCY, currencyAttributeValues
  [USD], nlsKeys}` → `{prices: [{price, product}]}`; 8 rows for `SPA_SERVICE`.
  POST only — a GET returns 500, keep the method exact.
- `POST …/catalog/products.json` → `{total, items}`;
  `GET …/catalog/products/{productId}.json`, `GET …/products/code/{code}.json`,
  `POST …/catalog/models.json`, `GET …/models/{modelId}/products.json`,
  `POST …/catalog/categories.json`, `…/types.json`,
  `…/types/{typeCode}/products.json`, review list/get, `catalog/restore.json`.
  The public detail surface the portal lacked (product by id/code, models,
  categories) **does exist** — W4 sellability reads can be anonymous-public.
- Authenticated tenant-level: generic CRUD for `product`, `product-model`,
  `product-price`, `product-review` (save **broken**), plus a full
  **Inventory API** (`inventory`, `inventory-transaction`, types, state
  transitions) — the missing piece for out-of-stock truth. Inventory rows for
  `SPA_RETAIL` must be seeded in S1 before sellability can be proven.

### 5. cart / checkout — cart **exists** (dedicated), checkout/quote **absent**

Dedicated server cart in core-bill (statically typed, first-class):

| operation | endpoint |
| --- | --- |
| read current cart | `GET /api/cart/current.json?accountId=…` |
| add/update item | `POST /api/cart/current/items.json` (body `CartItemRequest`) |
| change count | `POST /api/cart/current/items/{priceId}/count.json?accountId&delta` |
| remove item / clear | `DELETE /api/cart/current/items/{priceId}.json` / `DELETE /api/cart/current/items.json` |
| merge | `POST /api/cart/current/merge.json` (body `CartMergeRequest`) |
| anonymous restore | `POST /public/{organization}/cart/restore.json` |

Shapes: `CartView {id, organization, currency, notes, itemCount, subtotal,
items[]}`, `CartItemView {id, productId, productCode, priceId, currency,
unitAmount, count, lineAmount, notes, metadata}` — server-computed
`subtotal`/`lineAmount` satisfy the "cart totals are server-owned" rule.

Probes: missing `accountId` → **500** raw
`MissingServletRequestParameterException` (not a clean 400 — record as a
backend quirk); `accountId=1` under the SYSTEM deploy identity → **403
Forbidden**, i.e. the endpoint enforces a server-side account/user binding (or
a cart permission) beyond org RBAC. Characterizing that check (own → 200,
foreign → 403/404, missing → ?) is a mandatory S1 probe row.

**Gap:** no checkout-session, frozen-quote, or confirm endpoint. Confirmation
would be `order/save.json` (+ `order-item/save.json`) with `code`-idempotency
and readback. A server-frozen quote has no contract — W4 must either derive
the quote from the server cart response it just read (and re-validate on
confirm) or hold checkout per the stop condition.

### 6. orders / purchases — exists-generic

- `POST /core-bill/api/order/list.json` → 200, 4 rows live. Full generic
  family incl. `order-item`, `order-state-transition`, `order-item-state-transition`,
  type `SPA_SERVICE_ORDER` (`SPA_ORDER_LIFECYCLE`).
- Pagination is `offset/pageSize` (no cursor); "cursor list" from the master
  plan maps to offset paging — acceptable, record the deviation.
- Customer statuses map from workflow states; same tenant-level-scope caveat
  as appointments (client filter `account.id`, not a server boundary).

### 7. order recovery (cancel / return requests) — absent (dedicated), possible via workflow

- No request/cancellation/return endpoints. The lifecycle primitives are
  workflow events on `SPA_ORDER_LIFECYCLE` via `order/save.json` state writes
  or `order-state-transition` records.
- W4 decision input: model cancel/return as workflow events (needs event/
  permission design in the lifecycle seed) or as a new typed request entity.
  Neither exists today; keep `not_opened` until S1 proves the chosen shape.

### 8. plans (packages / memberships / balances) — partially exists, semantics unproven

- PIM products `SPA_MEMBERSHIP` / `SPA_PACKAGE` exist (offer side).
- core `entitlement-definition/list` → 200, 0 rows; `entitlement-grant/list`
  → 200, **2 rows** in the org — their semantics (RBAC/org grants vs customer
  plan instances) are uninspected. Master rule stands: org-RBAC entitlements
  must not be presented as an individual Spa plan.
- core-bill `subscription` family exists (list → 200, 0 rows) including a
  dedicated `subscription/create.json` and state transitions — the natural
  enrollment/renewal primitive.
- **Gap:** no balance/ledger endpoint anywhere; package-use counting has no
  server contract. S1 must inspect the 2 entitlement grants, and W5 needs an
  explicit product decision (subscription + entitlement-grant projection vs
  `not_opened` balances).

### 9. profile — exists-generic

- `POST /core/api/user/get.json` / `user/save.json` (email save + readback
  already proven by `core-user-profile-adapter`). `UserOrganizationPreferences`
  schema exists in core for per-org preferences.
- **Gap:** no server-side field whitelist; the client must send the full
  whitelisted patch with `optimistic` version. Field-level enforcement is a
  client discipline until a scoped profile contract exists.

## Authorization Truth (S0 summary → S1 input)

- Org boundary: `X-Organization-Code` + bearer works for every generic read
  probed; permission granularity is service/entity-level
  (`beautySpaCustomerPortalRbac.json` grants only self-service + PIM reads).
- Row-level isolation: **absent** on generic lists (client-sent filters), per
  the standing `CORE-CUSTOMER-PORTAL-CONTRACT.md` finding; unchanged.
- First positive counter-example: `cart/current` refused a browser-supplied
  `accountId` under a non-matching identity (403) — the only endpoint probed
  so far with a server-side account binding.
- S1 must therefore record, per boundary row, with a real `SPA_CUSTOMER_PORTAL`
  session: own / foreign / missing / multiple-account outcomes, and whether
  each fail is non-enumerating (same shape for foreign and missing).

## Live Defects and Quirks Found

1. core-pim ProductReview save broken (pre-existing; seeds use `--skip-reviews`).
2. `GET` on `price-comparison.json` → 500 (POST-only; not a defect to fix,
   a contract to respect).
3. `cart/current.json` without `accountId` → 500 with a raw Spring exception
   body instead of 400.
4. `public/{org}/catalog/price-comparison.json` with an unknown body shape
   also 500s rather than 400 — error semantics on public catalog are blunt.

## Verdict Against the W0 Stop Condition

Safe scoped **read** contracts exist (or are constructible with recorded
caveats) for boundaries 1, 2, 4, 5-cart, 6, 8-offers, 9. **No safe contract
exists** for: booking holds/slots (3), checkout frozen quote (5), cancel/return
requests (7), and plan balances/ledger (8) — these stay `not_opened` unless
W3–W5 accept the documented save+readback compromises or the backend ships the
missing contracts. S0 is complete: the matrix above is the exact endpoint and
contract inventory; S1 executes the seed and the authorization probe rows.
