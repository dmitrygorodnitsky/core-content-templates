## Подтверждённые проблемы

**1. Шесть отсутствующих CSS/JS.** По два в Use Cases, документации и Landscaping. Все шесть ссылок присутствуют в полученном HTML и возвращают 404. Вызовы DynamicForm на этих страницах не найдены. Вероятно, подключения старые, но удаление или замена — отдельное изменение; в этом аудите их не меняли. Перед загрузкой нужно либо восстановить файлы, либо проверить и согласовать исключение подключений.

**2. Landscaping: 18 изображений без содержимого.** Это не UUID из комментариев: ссылки есть в HTML страницы. Все возвращают HTTP 200 с нулевым телом; метаданные по этим ID не найдены. Нужны оригиналы или согласованные замены. Полные ссылки зафиксированы в JSON-реестре.

**3. Блог: иллюстрация и аватар.** Иллюстрация поста `/blog/service-wand-one-operational-system` и один аватар автора возвращают пустое тело. Для иллюстрации ранее найден файл с совпадающим именем `Service Wand and the Argument for One Operational System1.png`; это кандидат, а не подтверждённая замена потерянного оригинала. Нужно проверить изображение и явно утвердить замену. Аватар также нужно восстановить или согласовать его отсутствие.

**4. Landscaping: API тарифов требует входа.** Фактический запрос блока — POST `/core-pim/api/public/SERVICEWAND/catalog/price-comparison.json`; без авторизации он отвечает 401 на обоих серверах. Это уже существующая проблема источника. Не менять его молча на другой маршрут: проверить совместимость и сделать отдельное исправление.

**5. Блог: ссылки на пользователей-авторов.** У записей есть ссылки на User. Нельзя копировать их числовые ID на prod. При сборке нужно сопоставить существующих пользователей по устойчивой идентичности; создавать пользователей или назначать всем одного автора без решения нельзя. Отображаемое имя в metadata не заменяет эту связь автоматически.

## Что не является блокером загрузки, но требует аккуратной обработки

- **Три выключенные записи с permalink `snow-removal/blog-1`.** У двух нет текста. Не объединять и не включать их; permalink не использовать как единственный ключ. Различать записи по metadata, slug и отпечатку содержимого, а результаты создания фиксировать в журнале. Новые бизнес-поля для миграции не нужны.
- **Категории без slug.** У трёх категорий нет slug/permalink. Их имена внутри SERVICEWAND уникальны: при сопоставлении использовать организацию и локализованное имя с проверкой полного содержимого. Не придумывать URL категории.
- **Старая группа DOCUMENT_CODE.** У `/documentation/overview.html` есть значение `CORE_PLATFORM_OVERVIEW` для отсутствующего блока. Предлагается сохранить его в архиве и не назначать другому блоку, как в первом этапе.
- **Два старых фоновых изображения** присутствуют только в неиспользуемых параметрах юридических блоков старого дерева. В HTML страницы overview ссылок на них нет. Не считать их обязательными ресурсами показанной страницы; при упаковке отдельно архивировать или согласовать очистку этих параметров.
- **Видео Snow Removal доступно.** Проверенный маршрут страницы `/core/api/video/{id}/stream/{name}` отвечает 200. Проверка другого маршрута `/get` дала 401 и не является блокером этого видео.

## Тарифы: сохраняем prod

Snow Removal делает POST `/core-pim/public/SERVICEWAND/catalog/price-comparison.json`. На источнике и prod — HTTP 200. Вариант GET дал 500, но страница его не использует: это не её блокер.

Каталоги различаются:

| Позиция | servicewand.com | prod.servicewand.com |
|---|---:|---:|
| Foundation, USD / месяц | 99 | 199 |
| Foundation, USD / год | 990 | 1990 |
| Routing credits | Нет в ответе | Есть в ответе |

Динамический блок после переноса будет читать каталог prod. **При переносе CMS продукты и цены не перезаписываем.** Перед публичным запуском проверить, что отображение соответствует принятому каталогу; равенство HTML-цен и данных API не подразумевается.

## Что уже переиспользуем

- Десять страниц и 35 блоков первого этапа, FORM и десять определений форм остаются как есть.
- 76 файлов уже имеют проверенные целевые копии. Для остальных файлов перед загрузкой нужны бинарные хеши и поиск дублей по библиотеке, имени и хешу, а не по ID источника.
- Из семи нужных библиотек на prod есть четыре. Отсутствующие библиотеки сохраняют исходных владельцев SERVICEWAND или SYSTEM; переносим только нужные файлы, не всю системную медиатеку.
- AUTH и SAS не затрагиваем.

Проверка известных медиа: 224 image/media-asset endpoint ответили HEAD 200 с ненулевой заявленной длиной; видео проверено по stream-маршруту. Это не скачивание бинарного пакета и не доказательство равенства хешей.

## Порядок подготовки и будущей загрузки

1. Сопоставить организации, библиотеки, языки и авторов по устойчивым ключам. Для блоков использовать полный путь дерева; для страниц — организацию, site и URL.
2. Скачать нужные файлы, проверить SHA-256, сопоставить существующие копии prod. Разобрать повреждённые ссылки отдельно, без произвольных замен.
3. Для блога создать/сопоставить категории, затем записи с сохранением enabled, затем локализованное содержимое, media-ссылки и связи авторов. Все дубли сохранять различимыми.
4. Создать записи деревьев блоков, затем содержимое с разрешёнными ссылками. Загрузить PageContext, enabledTemplates и значения параметров.
5. Проверить чтение обратно, рендеринг, медиа, языки, навигацию, блог и тарифы на prod. Отправку форм проверять отдельно, без случайных заявок на источник.
6. Только после проверки всего сайта согласовывать переключение домена с backend. Сейчас переключения нет.
