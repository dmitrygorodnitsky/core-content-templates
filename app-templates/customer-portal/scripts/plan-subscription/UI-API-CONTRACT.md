# PLAN_SUBSCRIPTION: контракт БЛ → UI

Статус: **БЛ и native-доступ проверены на dev-1 23 октября 2026 года**. Пройдены
два FormToken, подготовка DRAFT, выдача тестового read-only AccessGrant, чтение
Order/строки, отказы для чужого ID, write/event и отозванного credential.
С 23 октября 2026 года на dev-1 есть покупательские страницы сайта ServiceWand:
`/subscribe.html`, `/subscribe-confirm.html`, `/subscription-order.html`
(исходники — `runtime/plan-subscription/`). Доставка через реальный почтовый
ящик не проверялась. Только CA, без User до оплаты и без включения оплаты.
Типы продуктов не меняются.

## Путь покупателя

1. Клиент отправляет существующую форму `PLAN_SUBSCRIPTION`.
2. Первое письмо содержит одноразовую FormToken для `VERIFY_EMAIL`. Существующий
   native маршрут подтверждает email; системная БЛ готовит Checkout.
3. Второе письмо показывает сохранённые данные, план, Add-ons, количества, строки,
   subtotal, а при готовом точном native расчёте — налоги и итог. При отсутствии
   налоговой настройки или согласованной точности суммы это явно обозначается.
   Отдельная одноразовая FormToken вызывает `CONFIRM_PURCHASE`.
4. После сохранённого согласия системная БЛ создаёт либо восстанавливает покупателя,
   DRAFT subscription Order, его строки и неоплаченный DRAFT Invoice при готовых
   налогах. Подтверждение не выполняет платёж.
5. Покупателю отправляется отдельное письмо со ссылкой на **чтение готового Order**.
   Ссылка содержит read-only AccessGrant на этот точный Order и его точные
   OrderItems. Он не создаёт User, сессию или общий доступ к организации.

До появления Order канал просмотра — второе письмо. Редактирование подтверждённой
формы через покупательский UI не требуется. Операторские `readCheckout`,
`reviseCheckout`, `readPurchaseStatus`, подготовка Invoice и онбординга остаются
внутренними командами. Их Script API и результаты jobs не открываются покупателю.
Новый Core API или обмен ссылки на покупательскую сессию для этого сценария не нужны.

## Два разных механизма ссылок

| Механизм | Назначение | Срок и повторение |
| --- | --- | --- |
| FormToken №1 | Подтверждение email конкретной формы | 24 часа, одноразовая |
| FormToken №2 | Согласие на конкретный подготовленный состав покупки | 24 часа, одноразовая; старый снимок не подтверждает изменившийся каталог |
| AccessGrant | Чтение конкретного сохранённого Order и его строк | 24 часа, повторное чтение разрешено до истечения или отзыва |

Существующий маршрут FormToken:

```text
POST /core-cms/api/form/send-event/{token}.json
```

Существует также native GET для ссылки из письма. Успешный ответ — **ID формы**,
не Checkout JSON и не credential для последующих чтений. Native ошибки включают
400 при отсутствии обязательных метаданных события, 404 для неизвестного token,
410 для уже использованного token. Срок и бизнес-валидность проверяет БЛ; UI не
должен выдумывать единый native HTTP-код для всех её ошибок.

Form ID, Order ID и Checkout digest сами по себе не дают права доступа.
Повторное открытие read-only AccessGrant не подтверждает покупку и не потребляет
повторно FormToken.

## Страница чтения и конфигурация URL

Публичный URL будущей buyer-страницы задаётся отдельным доверенным конфигом,
например в такой форме, **не как уже существующий маршрут**:

```text
https://<configured-host>/<configured-buyer-page>#orderId=<id>&token=<grant-token>
```

На dev-1 `purchase-access/config.json → pageUrl` —
`https://dev-1.servicewand.com/subscription-order.html`. Пустой `pageUrl` оставляет
статус `WAITING_FOR_PURCHASE_PAGE_URL`; **Grant заранее не выпускается**: его plaintext
token возвращается только один раз и не сохраняется для будущей отправки.

Ссылки из писем VERIFY_EMAIL и CONFIRM_PURCHASE ведут на страницу из метаданных
`CONFIRM_PAGE_URL` скрипта `PLAN_SUBSCRIPTION_WORKFLOW_V11`:
`<page>#step=verify|purchase&token=<form-token>`. Страница сама отправляет
`POST /core-cms/api/form/send-event/{token}.json` при открытии. Без
`CONFIRM_PAGE_URL` письмо ведёт на native endpoint, как раньше.

Этот URL отделён от `readyLoginUrl`, который ведёт в Core app для входа после
создания User. До оплаты покупатель не может использовать его как страницу чтения.
Native `order/get` — POST; обычный href прямо на этот API выполнит GET и не
заменяет buyer-страницу.

Token находится во fragment и не попадает в начальный запрос страницы. Будущий
UI читает его из fragment, использует только для native `/i/{token}/...` и убирает
из отображаемого URL после получения. Не помещает credential в CMS, query,
localStorage, аналитику, логи, сообщения об ошибках или внешние ссылки. Покупательские
данные не должны попадать в публичный кэш.

## Штатные native API после появления Order

Операции ниже предусмотрены native API. Чтение через наш issuer и точный mapping
проверено временным native-тестом; plaintext token оставался внутри тестового
процесса. Все его бизнес-записи и Grant удалены после проверки.

```text
POST /core-bill/i/{token}/introspect.json
POST /core-bill/i/{token}/order/get.json?id=<orderId>
POST /core-bill/i/{token}/order-item/get.json?id=<orderItemId>
POST /core-pim/i/{token}/product-price/get.json?id=<itemPriceId>
```

`ProductPrice` обслуживает сервис PIM: тот же token через `/core-bill/i/…` для цены
возвращает 404.

Introspection сообщает срок и доступные типы/операции, не раскрывает token или
содержимое чужих сущностей. При неизвестном, истёкшем либо отозванном Grant native
API возвращает отказ. На проверенном dev-1 чужой Order вернул 404, отозванная
ссылка — 401; попытки write/event с действующим read credential — 401/403.
UI обрабатывает 401/403/404 как отсутствие доступа и не раскрывает существование
чужой покупки. Не обещает единственный код 404 из общего руководства.

Order.items в разрешённом mapping возвращает только ID строк. Каждая строка
включается отдельным entry того же Grant; UI читает их отдельными native запросами.
Нет доступа к произвольному OrderItem по совпадению родительского Order.
Клиент не выбирает произвольные mappings, фильтры, seller или организацию.

## Точный доступ и поля

Entries Order и OrderItem делегируют **только `P_ORDER_R`**. С 23 октября 2026 года
grant также содержит по entry на каждую различную `itemPrice` строк заказа с
**только `P_PRICE_R`**: генерированный READ-потолок OrderItem даёт у `itemPrice`
лишь `id`/`nls` без продукта, а потолок ProductPrice включает `product {id, code, nls}`.
Не выдаются write, workflow event, audit/commit, delete, обычные Script permissions,
`P_GRANT_W` или административные роли. `writeMappings` явно пустые; readMappings —
только следующие поля:

| Сущность | Разрешённый READ mapping |
| --- | --- |
| Order | `id`; `currency {id, code, nls}`; `items {id}`; `states {id, code, nls}`; `type {id, code, nls}`; `totalCharges`; `totalTaxes`; `grandTotal` |
| OrderItem | `id`; `itemCount`; `amount`; `itemPrice {id, nls}`; `order {id}`; `type {id, code, nls}` |
| ProductPrice | `id`; `product {id, nls}` — название продукта строки, без атрибутов цены |

На dev-1 по такому grant цена вне заказа и прямой Product возвращают 404, список цен —
ровно цены заказа, запись цены — 401.

Не включаются root `attributes`, `metadata`, `account`, `notes`, owner/organization,
контакты, адреса, внутренние receipts, token hashes и результаты Script jobs.
Разрешённые вложенные объекты — ограниченные native summaries, а не полный граф
сущностей. Адрес и контакты клиент уже видел в письме.

Сервер выбирает точные Order/Item IDs из сохранённой подтверждённой покупки,
проверяет продавца, Account, receipt, состав и снимок. Изменённые/чужие строки,
другой Order или нарушенный receipt не должны получать Grant. Grant mapping
должен пройти действующую enabled mapping-политику с учётом native ceiling;
ошибка настройки закрывает выдачу, а не расширяет список полей.

Публичный статус здесь — **native Order state и суммы**. DRAFT означает неоплаченный
черновик; ACTIVE сам по себе не является публичным подтверждением всех шагов
онбординга. Внутренний `readPurchaseStatus` с private onboarding/error receipts
через этот Grant не публикуется.

## Выдача, доставка и восстановление

Выдача и отправка выполняются в billing после сохранённого одноразового согласия
и проверки готового Order. Настройка buyer URL проверяется до issue. Срок — 24 часа.
Получатель определяется подтверждённым email формы, не параметром анонимного запроса.

Issuer использует доверенный seller-контекст `SERVICEWAND` и настоящий UID
платформенного системного исполнителя. Внутреннюю CMS-команду может вызвать
SYSTEM-администратор; после проверки подтверждённой формы она передаёт в billing
только серверные данные от системного исполнителя. Минимальный временный server
context содержит только `P_GRANT_W`, `P_ORDER_R` и `P_PRICE_R` и восстанавливается в
`finally`. Persisted User/роли покупателя не создаются и не расширяются. В entries
попадают только `P_ORDER_R` (Order, OrderItem) и `P_PRICE_R` (ProductPrice).

Plaintext credential остаётся в памяти между `issue` и почтой. Он не возвращается
из асинхронного Script, не сохраняется в Form/Order metadata или workflow context.
В receipt существующего Order хранятся только grant ID, expiry, стадия доставки
и безопасные сведения для восстановления.

Перед отправкой фиксируется durable `DISPATCHING`. Повторный вызов не выпускает
ещё один Grant автоматически. Если результат почты неизвестен, выданный Grant
отзывается, receipt требует операторской сверки. Отказ отзыва тоже должен быть
видимым оператору; нельзя заявлять об успешном отзыве без его результата.
Успешная постановка в почтовую очередь не доказывает доставку адресату.
При сбое между issue/сохранением receipt/почтой нельзя повторно отправлять или
выпускать ссылки вслепую: сначала сверяется сохранённый Grant и исход операции.

## Деньги, Weather и выключенная оплата

Цены, количества, совместимость и налоги рассчитывает существующая серверная БЛ.
UI не пересчитывает их как независимый источник. Несовпадение каталога/налогов
с согласованным снимком требует нового просмотра и согласия. Точность валюты
проверяется сервером; отсутствие rounding policy не превращается в произвольное
округление или пригодный к оплате итог.

Weather пока имеет статус **`WEATHER_SETUP_PENDING`**: выбор и количество сохраняются,
активация и enforcement не реализованы. Нельзя писать, что Weather включён, или
предполагать, что существование продукта/Grant настроило реальные операции.
Routing и Custom Reports исключены; Enterprise — Contact us.

Оплата выключена. Read-only Grant не даёт оплаты, подтверждения платежа, запуска
онбординга, выдачи Entitlements или установки пароля. UI не вызывает Stripe и не
эмулирует успешную покупку. Онбординг и coverage требуют достоверного подтверждения
оплаты на сервере.

## Что остаётся команде

1. **Weather:** какие native операции/события и mapping включают/выключают Weather,
   учитывают его квоту и проверяют купленную фичу? Зачем: заменить stub реальной
   настройкой и брать оплату за выбранный Weather только когда его можно подключить.
2. **Будущая авторизация Stripe:** как покупатель без User получит intent своего
   Invoice, если существующий API требует вошедшего User с `P_USER` в организации
   продавца? Зачем: позже включить оплату без seller/SYSTEM credential в браузере и
   сохранить создание User после оплаты. Это отдельный вопрос от native read Grant.

Страница чтения работает на описанных native маршрутах, `pageUrl` на dev-1 заполнен.
Frontend вызывает API без seller Bearer и без cookies (`credentials: "omit"`) и не
кеширует ответы с данными покупки.
Для существующей ожидающей формы оператор повторяет защищённую команду
`deliverPurchaseReadAccess(formId, checkoutDigest)`; новые DRAFT запускают её через
workflow автоматически. Для проверки operator receipt есть `readPurchaseReadAccess`.

Пройдены 56 локальных policy assertions и focused native-тест
`check-dev1.mjs --apply --purchase-access-only`. Проверены сохранённая покупка,
ожидание URL, повтор команды, digest, изоляция, минимальный issuer, восстановление
контекста, чтение и отказ после отзыва. Это не тест прошедших 24 часов, реальной
почтовой доставки, платежа или создания клиентской организации: эти шаги выключены
либо пока не подключены к UI.
