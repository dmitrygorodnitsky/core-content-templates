# Snow Removal Operations — production deployment

On November 17, 2026, Core saved `SNOW-REMOVAL-OPERATIONS/DEFAULT` as a separate app with context `snow-removal-operations/index.html`. The request from `WINTER_SERVICES` returned 403 and created no record. The save from `SYSTEM` created the app; the app API did not return the submitted organization field, and Core registered the automatic app permissions in `SYSTEM`. The stored configuration and its read-back from the System context match the package. The entry HTML answered on both Core nodes, and a full download of the main JavaScript matched the local SHA-256.

Verified exactly two app-config read permissions were appended to each of Company Admin, Operations Manager, Dispatcher, Customer Support, Sales and Billing. The manual permission is under `WINTER_SERVICES`. The six roles retained all previous permissions and their organization. Driver and Customer Portal remained unchanged. Core's system Admin acquired the new app's permissions automatically on registration; no Admin role save was sent. The old `SNOW-CRM` metadata and available responses matched the baseline; no writes targeted that application. Schedule state was unchanged, and no payment operations ran.

Read-only invoice, paid invoice, billing order, route, routing run, routing template and visit queries returned 200 with the production filters from the System context. None of these queries returned rows in that context. The deployment credential cannot read the LSRC context (403); it does not establish what staff accounts can access.

Testing with a production staff login was left to the team, per the user. No test accounts were created. Before sharing the app broadly, open it with an existing LSRC account and confirm config access for that role. Then check Billing Order and paid-invoice behavior as Billing, and routes, templates and visits as Dispatcher.

In fresh browser sessions, some main JavaScript requests reset despite independent full downloads succeeding. In a session that downloaded the JavaScript, the unauthenticated localization request returned 403 and the page was still on Loading during the check. The same localization endpoint returns 403 without credentials on dev-1. Do not assume a working sign-in until a staff session is checked; if the cold load still stops, send backend the failing localization request and the page URL.
